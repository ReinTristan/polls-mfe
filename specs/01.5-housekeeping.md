# SPEC 1.5 — Housekeeping before federation


## Objective

Close the loose ends left by SPEC 01 before SPEC 02 introduces Module Federation and a real
Railway deploy. No features, no tooling changes that affect how the apps are built.

This milestone exists because of an ordering problem, not a scope problem. SPEC 02 is the riskiest
of the six, and debugging federation is easier in a repo whose paperwork is already straight than
in one that is also missing a README, a license and its decision records.

## Requirements

### R1 — A placeholder README

The repository currently has no entry point at all, and the full README is four milestones away in
SPEC 06 R5.

Add a short README that states **only facts that are verifiable today**: what the project is, the
status of each milestone, how to install and check it, and where each kind of decision is written
down. No claims about features that do not exist yet — SPEC 06's whole objective is turning README
claims into verified facts, so a README full of promises written now creates work there rather than
saving it.

Written in plain, everyday English, deliberately in a lighter register than `CLAUDE.md` and the
other specs.

### R2 — Minimal ADRs, all four

SPEC 06 R4 calls for four ADRs in `docs/adr/` following **Context · Decision · Alternatives ·
Consequences**. Write all four now at whatever depth the current state of the repo actually
supports, so the final versions can be compared against them later.

| ADR | Depth available today |
|---|---|
| 001 Module Federation over iframes or build-time integration | Decided, no evidence yet — SPEC 02 validates it |
| 002 Custom properties as the contract, not global CSS | Full argument: `@polls/tokens` is built |
| 003 A hand-written bus on `CustomEvent`, not MeBus or Postal.js | Full argument: the bus is built |
| 004 No Shadow DOM | Decided, no evidence yet — SPEC 04 validates it |

Each ADR carries a `Status` line saying which of those two it is. An ADR that invents consequences
nobody has observed is worse than a short one that admits the decision is still untested.

### R3 — Fix the `docs/adr/` gap from SPEC 01

SPEC 01 R2 lists `docs/adr` in the required structure and the criterion was marked met, but the
directory was only ever verified on disk with `ls`. Git does not track empty directories, so it
never entered the repository. R2 fixes this as a side effect; the criterion below re-checks it the
right way, with `git ls-files`.

### R4 — License

Add an MIT license. Without one, a public repository is legally closed by default — nobody may copy
or reuse it, which is the opposite of what a repository meant to be reviewed should say.

### R5 — Pin the TypeScript target, and explain the pnpm gate

Two configuration loose ends:

- `target` and `lib` sat at `esnext`, a moving target whose meaning changes with every TypeScript
  release, in a repository that pins Node and pnpm to exact versions. Pin them to `ES2025`.
- `pnpm-workspace.yaml` carries a `minimumReleaseAgeExclude` block that pnpm wrote by itself. It
  looked like leftover bookkeeping, but **it is load-bearing**: it is pnpm's supply-chain gate
  against freshly published packages, and `fastify@5.12.4` was still inside the window when it was
  installed. Removing it makes `pnpm install` fail outright. Keep it and explain it in a comment,
  rather than deleting something whose purpose was not understood.

## Acceptance criteria

- [x] `pnpm install` runs clean.
- [x] `pnpm biome check .` runs clean.
- [x] `pnpm typecheck` runs clean with the pinned `ES2025` target.
- [x] Git will actually track the four ADRs — verified with `git add --dry-run docs/`, since
      nothing is committed yet. `git ls-files docs/` is the final check once the commit lands.
      Checking the disk with `ls` is the mistake that let this slip through SPEC 01.
- [x] The API still boots on port 4000 and answers `/health` after the target change.
- [x] Every sentence in the README is true today, not true at SPEC 06.

## Out of scope

The full README (SPEC 06 R5), the definitive ADRs (SPEC 06 R4), and anything touching Vite, React
or Module Federation — that is SPEC 02.
